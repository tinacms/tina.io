## TinaCMS + Next: 第二部分

这篇博客是探索使用 Next.js + TinaCMS 系列的一部分。在[第一部分](https://tinacms.org/blog/simple-markdown-blog-nextjs/)中，你学习了如何使用 Next 创建一个简单的基于 Markdown 的博客。在这篇文章中，你将通过配置网站与 TinaCMS 来添加内容编辑功能。

### Next.js 回顾 ▲

[Next.js](https://nextjs.org/) 是一个由 [Vercel](https://vercel.com/) 团队构建的用于开发 Web 应用程序的 **React “元框架”**（一个基于框架构建的框架）。阅读[第一部分](/blog/simple-markdown-blog-nextjs/)以熟悉 Next.js 的基础知识。

### TinaCMS 概述 🦙

[TinaCMS](https://tina.io/) 是一个基于 Git 的无头内容管理系统，使开发人员和内容创作者能够无缝协作。使用 TinaCMS，开发人员可以创建一个完全适合其网站的自定义可视化编辑体验。

体验 TinaCMS 的最佳方式就是使用它。我们希望通过本教程，你不仅能学会如何使用 TinaCMS，还能了解 TinaCMS 如何重新思考 CMS 应该如何工作。

## 定义我们的内容结构

TinaCMS 的一个关键元素是定义一个架构，允许你塑造和与页面上的内容进行交互。打开项目，你会看到一个名为 `.tina` 的文件夹，其中包含一个 `schema.ts` 文件。此文件允许你指示 TinaCMS 的内容 API 查找哪种内容类型，如何标记它等等！

在查看当前项目之前，让我们讨论一下内容的结构。我们的架构可以分为三个概念：`collections`、`fields` 和 `references`。每一个都有其角色：

### Collections

架构中的顶级键是一个 *collections* 数组，一个 `collection` 告知 API *在哪里* 保存内容。在我们的指南中，我们将有一个 `posts` 集合，但你也可以有一个 `author` 和 `pages` 集合，例如。

### Fields

字段指示内容 API 预期的类型，例如 `text`，以及可查询的名称和要显示给你的内容团队的名称。字段是一个对象数组，是集合的子项。我们用它来从 Markdown 或 JSON 文件中检索内容，这些字段应映射到你的 *frontmatter*，我们还用它来创建用于编辑的 UI 元素。

```json
fields: [
    {
      type: "string",
      label: "Title",
      name: "title"
    },
    {
      type: "string",
      label: "Blog Post Body",
      name: "body",
      isBody: true,
    },
]
```

### References

这是一个重要的概念，当你 *引用* 另一个集合时，你实际上是在说：“这个文档 *属于* 那个文档”。一个很好的使用引用的例子是 *author*，因为每个帖子都会有一个作者，你可能有多个作者，但你需要将特定的作者引用到帖子中。

```json
{
  "label": "Author",
  "name": "author",
  "type": "reference",
  "collections": ["author"] // 指向一个名为 "author" 的集合
}
```

> 在我们继续之前，你可以在我们的[文档](/docs/schema/)中阅读更多关于内容建模的信息

### 对架构进行更改

打开位于 `/.tina/schema.ts` 的 TinaCMS `schema.ts` 文件。首先在我们提供的对象下方，你需要用你想要的内容替换当前集合：

到目前为止，你只替换了一行，即将 `path` 更新为博客内容的正确位置。

现在你需要处理每个字段的帖子前置内容，下面是完成的文件：

```js
import { defineSchema } from 'tinacms';

export default defineSchema({
  collections: [
    {
      label: 'Blog Posts',
      name: 'post',
      path: '_posts',
      fields: [
        {
          type: 'string',
          label: 'Title',
          name: 'title',
        },
        {
          type: 'string',
          label: 'Author',
          name: 'author',
        },
        {
          type: 'datetime',
          label: 'Date',
          name: 'date',
        },
        {
          type: 'string',
          label: 'Image',
          name: 'hero_image',
        },
        {
          type: 'string',
          label: 'Body',
          name: 'body',
          isBody: true,
        },
      ],
    },
  ],
});
```

你可能会注意到一些事情。首先，你有一个名为 `datetime` 的 `type`，它通过提供一个日期选择器供你使用，并将格式化日期和时间。

其次，有一个名为 `body` 的 `string` 字段，`isBody` 设置为 true。通过将 `isBody` 设置为 true，你是在声明这个字段负责 Markdown 文件的主要 *body*。只能有一个字段具有 `isBody: true` 属性。

### 下一步

你的 Markdown 文件现在由一个定义良好的架构支持，这为我们使用 GraphQL 查询文件内容铺平了道路。你会注意到在导航 Next.js 博客入门程序时没有任何变化，这是因为你需要更新入门程序以使用你的 GraphQL 层而不是直接访问 Markdown 文件。在下一节中，你将处理将前端转换为使用 TinaCMS。

目前，Next 博客入门程序从文件系统中获取内容。但由于 TinaCMS 在文件系统之上附带了一个 GraphQL API，你将改为查询它。使用 GraphQL API 将允许你利用 TinaCMS 的强大功能，你将能够检索内容，还可以直接编辑和保存内容。

## 创建 getStaticPaths 查询

`getStaticPaths` 查询需要知道你的所有 Markdown 文件的位置，使用当前架构，你可以选择使用 `postConnection`，它将提供 `posts` 文件夹中所有帖子的列表。确保你的本地服务器正在运行，并导航到 [http://localhost:4001/altair](http://localhost:4001/altair) 并选择 Docs 按钮。Docs 按钮使你能够查看所有可能的查询和返回的变量：

### 将此查询添加到你的博客中

上面的查询可以用来创建你的动态路径，这发生在 `[slug].js` 文件中。当你打开文件时，你会看到文件底部有一个名为 getStaticPaths 的函数。

```javascript
export async function getStaticPaths() {

....
```

删除此函数中的所有代码，你可以更新它以使用你自己的代码。第一步是在文件顶部添加一个导入，以便能够与你的 graphql 层进行交互。当你在那里时，你可以删除 `glob`，因为你将不再需要它。

```diff
//其他导入
.....
+ import { staticRequest } from "tinacms";
- const glob = require('glob')
```

> “staticRequest 是做什么的？”

> 它只是一个辅助函数，提供一个查询到你本地运行的 GraphQL 服务器，该服务器在端口 4001 上启动。你也可以轻松地使用 fetch 或你选择的 http 客户端。

在 `getStaticPaths` 函数内部，你可以构建对我们的内容 API 的请求。在发出请求时，TinaCMS 期望传递一个查询或变更，然后传递给查询的变量，这里是一个示例：

```javascript
staticRequest({
  query: '...', // 我们的查询
  variables: {...}, // 查询使用的任何变量
}),
```

你可以使用之前的 `postConnection` 查询来构建你的动态路由：

```js
export async function getStaticPaths() {
  const postsListData = await staticRequest({
    query: `
      query {
        postConnection {
          edges {
            node {
              _sys {
                filename
              }
            }
          }
        }
      }
    `,
    variables: {},
  });
  return {
    paths: postsListData.postConnection.edges.map((edge) => ({
      params: { slug: edge.node._sys.filename },
    })),
    fallback: false,
  };
}
```

#### `getStaticPaths` 的快速分解

`getStaticPaths` 代码采用你创建的 graphql 查询，因为它不需要任何 `variables`，你可以发送一个空对象。在返回功能中，你遍历 `postsListData.getPostList` 中的每个项目，并为每个项目创建一个 slug。

你现在需要创建另一个查询，这个查询将填充所有数据，并使你能够使所有博客帖子可编辑。

继续测试你的博客帖子是否仍然可读，例如导航到 [http://localhost:3000/blog/bali](http://localhost:3000/blog/bali)

## 创建 `getStaticProps` 查询

`getStaticProps` 查询将把所有内容传递给博客，这就是它目前的工作方式。当你使用 GraphQL API 时，TinaCMS 将同时传递内容，并使内容团队能够直接在浏览器中编辑它。

你需要从你的内容 API 中查询以下项目：

* author
* date
* hero\_image
* title

### 创建你的查询

使用你的本地 graphql 客户端，你可以使用博客帖子的路径查询 `post`，下面是你需要填写的骨架。

```graphql
query BlogPostQuery($relativePath: String!) {
  post(relativePath: $relativePath) {
    # 这是你想从帖子中检索的数据。
  }
}
```

> 如果你以前没有使用过 graphql，你会注意到一个奇怪的 `$relativePath` 后跟 `String!`。这是一个变量，String! 表示它必须是一个字符串并且是必需的。

你现在可以填写你需要查询的相关字段。在数据对象内部添加字段 author、date、hero\_image、title。你还希望检索博客帖子的正文，以便可以添加新内容。你应该有一个如下所示的查询：

```graphql
query BlogPostQuery($relativePath: String!) {
  getPostDocument(relativePath: $relativePath) {
    title
    date
    hero_image
    author
    body
  }
}
```

> 如果你想测试一下，你可以在底部的变量部分添加以下内容 `{"relativePath": "bali.md"}`

### 使用上下文编辑

你需要在博客上设置上下文编辑，以便可以使用我们的侧边栏编辑内容，类似于开头的演示。首先，你需要在页面顶部导入 `useTina` 钩子。

```javascript

```

> 什么是 `useTina`？

> `useTina` 是一个钩子，可用于使 TinaCMS 内容的一部分在上下文中可编辑。它是代码分割的，因此在生产环境中，这个钩子将简单地传递其数据值。在编辑模式中，它在侧边栏中注册一个可编辑的表单，并在用户输入时上下文地更新其值。

你现在可以将你创建的查询用作变量，这个变量将在你的 `getStaticProps` 和 `useTina` 钩子中使用。

```javascript

    date
    hero_image
    author
    body
  }
}`;
```

#### 替换你的 getStaticProps

要替换你的 getStaticProps，你将使用 `staticRequest`，类似于我们在 `getStaticPaths` 代码中使用的方式。

首先要做的是删除你不再需要的所有代码，包括 `content` 和 `data` 变量以及 `markdownBody`、`frontmatter` 从你的 props 中删除。

```diff

- const content = await import(`../../posts/${slug}.md`)
  const config = await import(`../../data/config.json`)
- const data = matter(content.default)

    props: {
       siteTitle: config.title,
-      frontmatter: data.data,
-     markdownBody: data.content,
    },
  }

```

现在你已经从代码中删除了这些内容，你可以使用我们的 `staticRequest` 来检索数据。这次唯一的区别是你实际上需要一个名为 `relativePath` 的变量，它是 slug。你还需要将变量作为 prop 发送，以便可以在我们的 `useTina` 钩子中使用它。

```javascript
export async function getStaticProps({ ...ctx }) {
  const { slug } = ctx.params
  const config = await import(`../../data/config.json`)
  const data = await staticRequest({
    query,
    variables = {
      relativePath : slug,
    },
  })
  return {
    props: {
      data,
      variables,
      siteTitle: config.title,
    },
  }
}
```

### 添加 Markdown 支持

要添加 Markdown 支持，你需要做两件事。

1. 告诉 TinaCMS 如何使用不同的组件。
2. 动态加载 Markdown 组件。

#### 更新 TinaCMS 架构

打开位于 `.tina` 文件夹中的 `schema.ts`。TinaCMS 的一个伟大之处在于你可以扩展 UI 字段以满足你的确切需求，为此你可以使用 `ui` 对象并告诉 TinaCMS 你想使用的组件。

```typescript
ui: {
  component: COMPONENT_NAME;
}
```

你想使用 Markdown 组件，因此你可以覆盖你的正文，它应该如下所示：

```typescript
{
  type: 'string',
  label: 'Body',
  name: 'body',
  isBody: true,
  ui: {
    component: 'markdown'
  }
},
```

#### 更新 `_app.js`

在打开你的 `_app.js` 文件之前，你需要从 TinaCMS 安装 Markdown 插件。

```bash,cp
yarn add react-tinacms-editor
```

打开你的 `_app.js` 文件，这里你将使用 `TinaCMS` 组件的 `cmsCallback` prop，它允许你扩展默认功能，添加插件，处理文
