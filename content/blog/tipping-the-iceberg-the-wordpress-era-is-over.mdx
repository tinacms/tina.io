On October 21, 2026, the PHP project released emergency fixes for 2 critical vulnerabilities: CVE-2026-109618 and CVE-2026-109619, known together as **PHP2Shell**.

- Both flaws can let an attacker run code on your server without logging in
- The flaws are in PHP, not WordPress or a plugin. A WordPress update doesn't fix them.
- Update PHP, or ask your host to

Both flaws affect PHP's memory and error handling, used by nearly every request.
An attacker triggers a failure at a chosen point, such as the memory limit, then exploits what remains in memory.
The PHP Foundation's [retrospective](https://thephp.foundation/blog/2026/10/21/todays-php-security-release-and-how-were-strengthening-php-security/) has the details.

The advice was to go offline, and some did:

- On October 21, [CISA's alert](https://www.cisa.gov/news-events/alerts/2026/10/21/critical-vulnerabilities-php-require-immediate-patching) said organizations that can't update right away *"should take PHP-based systems offline until they can be patched or updated"*
- The [Dutch government](https://www.rijksoverheid.nl/actueel/nieuws/2026/10/21/aantal-websites-rijksoverheid-preventief-offline-na-kwetsbaarheden-php) took Overheid.nl, MijnOverheid and DigiD offline as a precaution
- Email alias service [addy.io](https://status.addy.io) shut down its web systems for about 3.5 hours *"due to the PHP2Shell vulnerability"*. Its own code wasn't broken.

## PHP fix: Patch now

[WordPress runs on PHP](https://wordpress.org/about/requirements/), so you patch PHP itself.
There are 2 ways, depending on who runs PHP:

- **A managed host runs it.** Ask your host to confirm they applied both fixes and restarted PHP.
- **You run the server.** Update PHP to the fixed release for your version, then restart the services that use it:
  - **8.5.12**
  - **8.4.27**
  - **8.3.36**
  - **8.2.35**
  - PHP 8.1 and older get no fix from the PHP project, so get vendor guidance

To see a site's PHP version, open **Tools > Site Health > Info > Server** in WordPress.

Risk is highest on Apache with `mod_php`.
Researchers showed an attack there that runs before any application code, so a WordPress login can't protect you.
Exposure is a reason to patch, not proof of a break-in.
See the [PHP security advisory](https://www.php.net/archive/2026.php) for details.

## The bigger question: does this site still need PHP?

Clients know the WordPress editor, and your team knows how to deliver sites with it.
But you also maintain everything under the pages.

WordPress is open source, and you can [export your content](https://wordpress.org/documentation/article/tools-export-screen/).
Changing hosts doesn't remove PHP.
Using WordPress headlessly with Astro or Next.js keeps PHP because WordPress remains the content backend.
Removing PHP means replacing WordPress.
That can involve untangling themes, page-builder layouts, custom fields and publishing workflows.

To size that cost, ask:

- How much content is useful outside the current theme and plugins?
- Can another developer rebuild the site from documented access, or does it depend on one person's memory?

## Better solution: Keep the content, change what runs it

TinaCMS stores content as Markdown, MDX and JSON files in your Git repository.
Editors get a CMS interface, and each save is a commit.
[TinaCloud](https://tina.io/docs/tinacloud) runs the editor backend, or you can self-host it.

You build the frontend with Astro, Next.js or another React framework.
The editing experience varies by framework, as the [framework guide](https://tina.io/docs/integration/frameworks) shows.
Because the content is plain files, a later frontend change means new templates, not a content migration.
Plain Markdown moves easily; MDX with custom React components needs more work.

### A new stack still needs care

- TinaCMS, your frontend, hosting and build tools need updates
- A static site can serve pages from a CDN without running the CMS on each visitor request. Editing and build systems still need protection.
- A static site keeps serving pages if TinaCloud or your self-hosted backend goes down. Editing and new builds wait until it returns.
- Forms, site search and personalized pages need their own plan

Without a PHP runtime, respond to PHP2Shell by checking the stack, then get back to work.

### Try it with a pilot

1. Start a TinaCMS project: `npx create-tina-app@latest`
2. Pick 2 or 3 representative pages, including an awkward layout
3. Move content and media with our [WordPress to TinaCMS guide](https://tina.io/docs/guides/converting-wordpress-to-tina). Design and plugin behavior need separate work.
4. Keep existing URLs, or map redirects
5. Have a real editor do their normal tasks on a preview deployment
6. Ask another developer to build and deploy from the docs, then restore an earlier page version
7. List where leads, orders and customer records live. They need their own migration plan.
8. Compare the maintenance cost with the current site
