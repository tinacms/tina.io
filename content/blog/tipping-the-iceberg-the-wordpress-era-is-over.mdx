On 21 October 2026, the PHP project released emergency fixes for two critical vulnerabilities: CVE-2026-109618 and CVE-2026-109619, known together as **PHP2Shell**.

**In short:**

- Both flaws can let an attacker run code on your server without logging in.
- They are in PHP itself, not in WordPress or a plugin. A WordPress update doesn't fix them.
- Update PHP, or get your host to. Then ask a bigger question: does this site still need PHP?

In plain terms: when a request fails at the wrong moment, for example by running out of memory, PHP can leave broken data behind, and a later request can use it to run code. The PHP Foundation's [retrospective](https://thephp.foundation/blog/2026/10/21/todays-php-security-release-and-how-were-strengthening-php-security/) has the details. One PHP app, addy.io, [took its website and web app offline](https://addy.io/blog/addy-io-went-offline-for-the-php2shell-vulnerability/) for about 3.5 hours while it patched.

If you maintain client sites, picture explaining that. The site looks fine. Your client changed nothing. A dependency underneath it needs an urgent fix, and your afternoon is gone.

## Patch now

[WordPress requires PHP](https://wordpress.org/about/requirements/), so a WordPress site is exposed until its PHP is patched. What you do depends on who runs PHP:

- **A managed host runs it.** Ask them: *"Have you applied the fixes for both CVEs to the PHP environment serving our site, and restarted any affected services?"* Do not assume. In `r/sysadmin`, one developer [put it simply](https://www.reddit.com/r/sysadmin/comments/1xc4rjx/php2shell_and_your_security_team/): *"I'm on WordPress, and I can't patch my websites"*. Their host had not released the update.
- **You run the server.** Update PHP to **8.5.12**, **8.4.27**, **8.3.36** or **8.2.35**, and restart the services that use it. PHP 8.1 and older get no fix from the PHP project, so get vendor guidance.

Good to know:

- To find a site's PHP version, open **Tools > Site Health > Info > Server** in WordPress.
- Risk is highest on Apache's mod_php, where a demonstrated attack can trigger before any application code runs. There, a WordPress login can't protect you.
- Exposure is a reason to patch, not proof of a break-in.
- For details, follow the [PHP security advisory](https://www.php.net/archive/2026.php) and the [CISA alert](https://www.cisa.gov/news-events/alerts/2026/10/21/critical-vulnerabilities-php-require-immediate-patching).

## The bigger question: does this site still need PHP?

WordPress enters projects for good reasons: the client knows the editor, and your team knows how to deliver it. Over time, though, you also maintain everything under the pages:

- The PHP runtime, WordPress core and the plugins.
- Which updates need care.
- Which integration someone added years ago.
- Which account can restore a backup.

![Two icebergs. The WordPress iceberg shows pages above the water and a large mass below it: PHP runtime, WordPress core, plugins and theme, hosting and patches, backups and old integrations. An arrow points to a smaller TinaCMS iceberg: pages above the water, and only content files in Git, frontend and build, and static hosting below it.](/img/blog/tipping-the-iceberg-the-wordpress-era-is-over/wordpress-to-tinacms-iceberg.png)

WordPress is open source, and you can [export your content](https://wordpress.org/documentation/article/tools-export-screen/). But changing hosts doesn't remove PHP, and neither does a headless setup with [Astro](https://astro.build/) or [Next.js](https://nextjs.org/): WordPress stays the content backend, and that backend needs PHP. To remove PHP, you replace WordPress. That can mean untangling themes, page-builder layouts, custom fields and publishing workflows.

To size that cost, ask:

- How much of the content is useful outside the current theme and plugins?
- Can another developer rebuild the site from documented access, or does it depend on one person's memory?

## Keep the content, change what runs it

- TinaCMS stores content as Markdown, MDX and JSON files in Git. Editors get a CMS interface, and each save is a commit to your repository.
- [TinaCloud](https://tina.io/docs/tinacloud) connects the editor and content API to that repository, which stays the source of truth. Its query index can be rebuilt from the files. You can also [self-host the backend](https://tina.io/docs/self-hosted/overview).
- Build the frontend with Astro, Next.js or another React integration. The [framework guide](https://tina.io/docs/integration/frameworks) lists them; the editing experience varies by framework. Content can also live in a [separate content repository](https://tina.io/docs/guides/separate-content-repo).
- A later move from Next.js to Astro means rebuilding templates and components, not migrating content. Plain Markdown moves easily; MDX full of custom React components needs more work.
- TinaCloud's [Editorial Workflow](https://tina.io/docs/tinacloud/editorial-workflow) adds branches and draft pull requests for content changes, on select paid plans.

## A new stack still needs care

- TinaCMS, your frontend, hosting and build tools all need updates.
- A static site can serve pages from a CDN without running the CMS on each visitor request. Editing and build systems still need protection.
- Forms, search and personalized pages need their own plan.

With no PHP runtime, the PHP2Shell response is short: check the stack and get back to work.

## Try it with a pilot

Start a TinaCMS project with one command:

```bash
npx create-tina-app@latest
```

Then:

1. Pick 2 or 3 representative pages, including an awkward layout.
2. Move the content and media with our [WordPress to TinaCMS guide](https://tina.io/docs/guides/converting-wordpress-to-tina). Design and plugin behavior need their own work.
3. Keep existing URLs, or map redirects.
4. Have a real editor do their normal tasks on a preview deployment.
5. Ask another developer to build and deploy it from the docs, then restore an earlier version of a page.
6. List where leads, orders and customer records live. They need their own migration plan.
7. Compare the maintenance cost with the current site.

An AI coding assistant can scaffold the pilot from a screenshot. Our [vibe blogging walkthrough](https://tina.io/blog/vibe-blogging-with-tinacms) shows how.
