We care a lot about developer experience at TinaCMS, and TypeScript is at the core of it. So wherever we can give you a proper type instead of `any`, we want to.

Rich-text fields have been the exception. From `@tinacms/cli` 3.0.0, they come back as `TinaMarkdownContent`, the same type `<TinaMarkdown>` already expects.

## Show me the code

In `tina/__generated__/types.ts`, the type for a post query changes like this:

```ts
// Before
export type PostQuery = { post: { title: string, _body: any } };

// After
export type PostQuery = { post: { title: string, _body: TinaMarkdownContent | null } };
```

With `any`, both of these lines compiled fine and then blew up at runtime:

```tsx
const excerpt = data.post._body?.slice(0, 160);
const count = data.post._body?.childrn.length;
```

Now TypeScript catches them:

```tsx
const excerpt = data.post._body?.slice(0, 160);
// Property 'slice' does not exist on type 'TinaMarkdownContent'.

const count = data.post._body?.childrn.length;
// Property 'childrn' does not exist on type 'TinaMarkdownContent'. Did you mean 'children'?
```

Your editor also suggests `type` and `children` as you type.

When we first switched this on, our own kitchen-sink example failed to compile in two places where it passed an optional body to `<TinaMarkdown>`. Our first fix was a null check at each call. The component already renders nothing for a `null` body, though, so we fixed its types in `tinacms` instead, and you can pass the field straight in:

```tsx
// Before
{data.post._body && <TinaMarkdown content={data.post._body} />}

// After
<TinaMarkdown content={data.post._body} />
```

If you have components that take rich text as a prop, swap `any` for `TinaMarkdownContent` to get the same checks there:

```tsx
import { TinaMarkdown, type TinaMarkdownContent } from 'tinacms/dist/rich-text';

export const Callout = ({ body }: { body: TinaMarkdownContent }) => (
  <aside className="callout">
    <TinaMarkdown content={body} />
  </aside>
);
```

## Why `_values` is still `any`

Every document in the GraphQL API also has a `_values` field, which returns all of its fields as one JSON object. We tried typing it as `unknown`, but projects that read documents through it, like our [self-hosted demo](https://github.com/tinacms/tinacms/tree/main/examples/next/tina-self-hosted-demo), would need a cast on almost every line, and a cast is no safer than `any`. The better fix is a generated type for each collection's `_values`, and we're looking at that once [v4](https://tina.io/blog/tinacms-v4-is-coming) lands.

## Upgrading

Update `tinacms` and `@tinacms/cli` together:

```bash
pnpm update --latest tinacms @tinacms/cli
# or
npm install tinacms@latest @tinacms/cli@latest
```

Start your dev server so the CLI regenerates your types, then run `tsc --noEmit` to see what TypeScript finds. Your queries and content don't change. For most projects, that's it.

If a rich-text field still comes back as `any` after you upgrade, or TypeScript flags code you think is fine, open an [issue](https://github.com/tinacms/tinacms/issues) or come and find us on [Discord](https://tina.io/discord).
